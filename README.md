# cube-components

My own [shadcn/ui](https://ui.shadcn.com) components, published as a **shadcn registry** so any of my projects can install them with the shadcn CLI, the same way you'd install `button` or `dialog`.

- **Demo:** https://cubityfirst.github.io/cube-components/
- **Registry index:** https://cubityfirst.github.io/cube-components/r/registry.json

| Component | Install |
| --- | --- |
| Color Picker | `npx shadcn@latest add https://cubityfirst.github.io/cube-components/r/color-picker.json` |

---

## How this works (and why it's not an npm package)

shadcn components aren't installed as dependencies. They're **copied into your project as source**, then they're yours to edit. A *registry* is just a set of JSON files, one per component, that tells the shadcn CLI:

- the component's source code
- which npm packages it needs (`dependencies`), e.g. `@base-ui/react`
- which other shadcn components it needs (`registryDependencies`), e.g. `button`, `input`

When you run `npx shadcn add <url>`, the CLI downloads that JSON, writes the file into your `components/ui` folder, **rewrites the imports** (`@/lib/utils`, `@/components/ui/button`) to match that project's `components.json` aliases, installs the npm deps, and adds any missing shadcn components in your project's style.

That's why it beats npm here. The component uses your project's `cn`, `Button`, `Input` and theme tokens, and Tailwind sees its classes as ordinary source, with no build step, peer deps or `@source` config.

```
registry.json                  ← list of components in this registry (the source of truth)
src/registry/ui/*.tsx          ← the component sources that get published
src/App.tsx                    ← demo page (imports from src/registry)
public/r/*.json                ← generated by `npm run registry:build` (git-ignored)
.github/workflows/deploy.yml   ← on push to main: build registry + demo → GitHub Pages
```

Every push to `main` rebuilds the registry and demo and deploys them to GitHub Pages, so the install URLs always serve the latest `main`.

## Using it in another project

### Requirements

- A shadcn project using **Tailwind CSS v4** (`npx shadcn@latest init`)
- **Base UI** style recommended (`npx shadcn@latest init -b base`). Radix-style projects also work: the picker only uses `Button`/`Input` props common to both, and brings its own `@base-ui/react` dependency for the sliders.

### Install

```bash
npx shadcn@latest add https://cubityfirst.github.io/cube-components/r/color-picker.json
```

### Optional: a short `@cube/` name

Add this to the project's `components.json`:

```json
{
  "registries": {
    "@cube": "https://cubityfirst.github.io/cube-components/r/{name}.json"
  }
}
```

Then:

```bash
npx shadcn@latest add @cube/color-picker
```

### Updating

Components are copies, so updates are pulled manually. Re-run the `add` command to overwrite your copy with the latest version. If you've customised the file locally, check the diff before committing.

## Components

### Color Picker

A saturation/brightness area plus **Hue → Saturation → Lightness → Alpha** bars. Each bar previews the colour you'd get at every position, based on the current colour.

```tsx
import { ColorPicker } from "@/components/ui/color-picker"

const [color, setColor] = useState("#3b82f6")

// Default layout: area, H/S/L bars, (alpha bar), swatch, hex input, eyedropper
<ColorPicker value={color} onValueChange={setColor} />
```

Compose your own layout:

```tsx
import {
  ColorPicker,
  ColorPickerArea,
  ColorPickerHue,
  ColorPickerSaturation,
  ColorPickerLightness,
  ColorPickerAlpha,
  ColorPickerSwatch,
  ColorPickerInput,
  ColorPickerEyeDropper,
} from "@/components/ui/color-picker"

<ColorPicker value={color} onValueChange={setColor} alpha>
  <ColorPickerArea />
  <ColorPickerHue steps={12} />
  <ColorPickerSaturation />
  <ColorPickerLightness />
  <ColorPickerAlpha />
  <div className="flex items-center gap-2">
    <ColorPickerSwatch />
    <ColorPickerInput />
    <ColorPickerEyeDropper />
  </div>
</ColorPicker>
```

**`<ColorPicker>`**

| Prop | Type | Default | |
| --- | --- | --- | --- |
| `value` / `defaultValue` | `string` | `#3b82f6`-ish | Hex: `#rgb`, `#rrggbb`, `#rrggbbaa` |
| `onValueChange` | `(hex, hsva) => void` | | Fires continuously while dragging/typing |
| `onValueCommit` | `(hex, hsva) => void` | | Fires once when an interaction ends |
| `alpha` | `boolean` | `false` | Shows the alpha bar; output becomes `#rrggbbaa` when not fully opaque |
| `disabled` | `boolean` | `false` | |

Renders a default layout when it has no children.

**Bars** (`ColorPickerHue`, `ColorPickerSaturation`, `ColorPickerLightness`, `ColorPickerAlpha`) accept Base UI `Slider.Root` props, plus:

| Prop | Type | Default | |
| --- | --- | --- | --- |
| `steps` | `number` | | Split the bar into N swatches showing the exact colour of each step; the thumb snaps to them |
| `live` | `boolean` | `true` | Preview each position against the current colour. `false` shows the standard full-strength gradient |
| `orientation` | `"horizontal" \| "vertical"` | `"horizontal"` | |

`ColorPickerAlpha` renders nothing unless the root has `alpha`.

**Colour models:** the big area is HSV (saturation → right, brightness → up), which is the standard for this kind of square. The bars are HSL. Both control the same colour, and HSL saturation is kept when you pass through pure black/white, so the bars don't jump.

**Also exported:** `useColorPicker()` for building your own parts, and helpers `hexToHsva`, `hsvaToHex`, `hsvaToRgba`, `rgbaToHsva`, `hsvaToHsla`, `hslaToHsva`, `hsvaToCss`, `hslaToCss`.

**Keyboard:** arrow keys move the area (Shift = ×10). Bars behave like standard sliders (arrows, Page Up/Down, Home/End). The hex input applies on Enter or when you click away, and Escape reverts it.

## Developing

```bash
npm install
npm run dev              # demo page at http://localhost:5173
npm run registry:build   # regenerate public/r/*.json
npm run build            # registry + typecheck + demo → dist/
```

### Adding a new component

1. Write it in `src/registry/ui/<name>.tsx`. Import shared things via the normal shadcn aliases (`@/lib/utils`, `@/components/ui/button`); the CLI rewrites them for each consumer.
2. Add an entry to `registry.json`:
   ```json
   {
     "name": "my-thing",
     "type": "registry:ui",
     "title": "My Thing",
     "description": "…",
     "dependencies": ["some-npm-package"],
     "registryDependencies": ["button"],
     "files": [{ "path": "src/registry/ui/my-thing.tsx", "type": "registry:ui" }]
   }
   ```
   - `dependencies`: npm packages to install.
   - `registryDependencies`: shadcn components (`"button"`), or other items from this registry by full URL.
3. Show it off in `src/App.tsx`, then push to `main`. It'll be live at `…/r/my-thing.json` after the Pages deploy finishes.

The shadcn components used by the demo itself (`src/components/ui/button.tsx` etc.) are ordinary shadcn installs and are **not** published.
